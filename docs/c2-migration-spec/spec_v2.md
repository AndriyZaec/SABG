# CS2 Discipline — Specification v2

> Додає **Discipline** як наскрізну концепцію та CS2 як першу нефутбольну дисципліну. Дані —
> з GRID (`seriesState` GraphQL), не з TxODDS. Фокус розробки зараз — CS2; football активно не
> розвивається паралельно. Точки розширення під майбутні дисципліни закладені свідомо, без
> передчасної уніфікації round-engine логіки між дисциплінами (вона лишається дисципліно-
> специфічною, §3).

## 1. Концепція

CS2: серія (`best-of-N`) → карти (кожна = один `Match`) → раунди. На відміну від soccer
(фіксовані 5-хв windows, час іде вперед):

- раунд завершується подією (перемога команди), не таймером;
- немає єдиного матчевого годинника: `freezetime` (закупівля) → live-раунд (годинник тікає
  **назад**) → наступний раунд;
- дані — кумулятивний стан-снепшот кожні ~10с (GRID `seriesState`), не потік дискретних подій.

CS2 отримує окремий, паралельний round engine — не модифікацію soccer-специфічного.

## 2. Терміни

| Термін | Означення |
|---|---|
| **Discipline** | Тип гри (`soccer`, `cs2`, розширювано далі), поле `discipline` на `Match`; визначає реалізацію round engine, question-provider та ingestion. |
| **Match** (`@arena/contracts`) | Дисципліно-агностична сутність: **1 Match = 1 Arena завжди**, для всіх дисциплін однаково. Для soccer — весь матч, без зв'язку з Series. Для CS2 — одна карта, з `seriesId?` на `Series`. |
| **Series** (нова сутність) | `best-of-N` угруповання Match-рядків (по одному на карту), відповідає GRID `seriesState`. Поля: `format: number` (1–7), `scheduledStartTime`. **Не Arena** — Arena завжди на рівні одного Match. `Match.seriesId?` — FK; дисципліни без серійної структури (soccer) лишають порожнім. |
| **Game** (GRID-термін) | Не наша сутність — назва об'єкта в GRID API (`seriesState.games[]`), що відповідає одному нашому `Match`-рядку для CS2. Вживається в цій специфікації лише там, де йдеться про сире GRID-поле чи функцію (`hasLiveGame()`, `games[0].teams[]`). |
| **Round (CS2)** | Ігровий раунд усередині Match (карти). Номер виводиться: `sum(games[0].teams[].score) + 1` (не зберігається напряму в GRID). |
| **PredictionRound** (`@arena/contracts`) | Вікно питання/ставки; для CS2 — 1:1 з реальним Round. |
| **Pistol Round** | Round 1 і Round 13 кожного Match (формат MR12: два пів по 12) — домен-факт, обидва визначаються арифметично за номером раунду, без стороннього economy-поля. **Фіксоване pistol-питання ставиться тільки на Round 13** (§7, §10) — Round 1 такого спецстатусу в питаннях більше не має. |
| **Match Live Detected** | GRID вперше показує відповідний об'єкт Game у `seriesState.games` (фільтр `started:true, finished:false`) — з'являється вже під час warmup, до старту Round 1. |
| **Round Lock (CS2)** | Кінець freezetime поточного раунду (момент, коли live-годинник починає тікати вниз) — не абсолютний час. |

## 3. Точка розширення для майбутніх дисциплін

- **`Match.discipline: Discipline`** — enum `"soccer" | "cs2"`, розширюваний. Round
  engine/question-provider/ingestion обираються фабрикою за цим полем через існуючий DI-seam
  (`RoundEngine` вже приймає інжектований `QuestionProvider`).
- **`Match.seriesId?`** — FK на `Series` (§2). Легка сутність без власного round-engine чи
  Arena-логіки, але зберігає дані (`format`, `scheduledStartTime`), що керують реальною
  бізнес-логікою (§4).
- **Внутрішня логіка round engine свідомо НЕ уніфікується** між дисциплінами (fixed windows на
  годиннику матчу для soccer vs event-driven каскад для CS2) — окремі реалізації
  `QuestionProvider`. Примусова спільна абстракція над принципово різними доменами (таймер vs
  подія) була б передчасною.
- **Join/lobby-правило CS2-специфічне** (join до Match Live Detected, §5), реалізується як
  CS2-specific перевірка в Arena join-хендлері (аналог `hasLockedRound()`, але за умовою Match
  Live Detected) — без зміни generic Arena API.
- **Tie-break наприкінці Match перевикористовує generic-правило** spec (soccer) §12 "shared win
  → рівний поділ призового пулу між tied winners" — якщо Match завершується (команда набрала
  потрібну к-сть перемог), а кілька гравців ще живі без помилки. Нового CS2-специфічного
  критерію не потрібно.
- **Фіксовані спеціальні раунди** (pistol round 13, OT-питання round 24, §7) — CS2-специфічний хук
  у CS2-реалізації `QuestionProvider`, не generic-концепція в contracts.

## 4. Arena lifecycle через Series

**Створення Arena:**

1. **Arena #1** (перший Match у Series) створюється автоматично в стані `lobby` за **10 хв** до
   `scheduledStartTime`. Join відкритий одразу, закривається на Match Live Detected (§5).
2. **Arena #k+1** створюється реактивно одразу по завершенню Match k (`hasLiveGame()` стає
   `false` для відповідного GRID Game-об'єкта) — за умови, що Series ще не вирішена (крок 3).
   Номер `k+1` — власний послідовний лічильник, не потребує звірки з GRID `sequenceNumber`.
3. **"Series вирішена"** — Arena #k+1 НЕ створюється, якщо виконується будь-яка з умов:
   - `k >= format` (усі ігри формату зіграно);
   - будь-яка команда досягла `winsNeeded = floor(format / 2) + 1` перемог
     (`seriesState.teams[].score`).

   Обидві умови потрібні через **Bo2** (`format = 2`, можлива нічия 1-1): `winsNeeded = 2`
   дорівнює `format`, тобто early clinch спрацьовує лише на sweep 2-0, а нічию 1-1 ловить
   `k >= format`. Для непарних форматів (Bo3/5/7) нічия неможлива, обидві умови завжди
   збігаються. Правило одночасно покриває нормальне дострокове завершення, нічию у Bo2 та
   форфейт всередині Series.
4. **No-show на першому Match у Series**: якщо Match Live Detected не настає протягом **60 хв**
   після `scheduledStartTime` → Arena #1 переводиться в `cancelled`, **вся Series позначається
   недійсною**, усі куплені `EntryPass` → `status: refunded`.
5. **Форфейт всередині live Match** — окремого правила не потрібно: покривається загальним
   "Match завершився" (`hasLiveGame() === false`), tie-break за §3.

**Незалежність Match-рядків у межах Series**: кожен Match (карта) — повністю окрема Arena з
власним `EntryPass`, survival-станом і призовим пулом, що розподіляється одразу по завершенню
цього Match. Елімінація на Match 1 не впливає на вхід в Arena для Match 2.

**Push-нотифікація "нова Arena відкрита"** — усім учасникам попередньої Arena Series при
створенні Arena #k+1 (окремо від per-round нотифікації, §6).

## 5. Join / Lobby правила

Join в Arena дозволений **тільки до моменту Match Live Detected** (§2). Після — Arena закрита
для нових гравців (тільки spectate), навіть якщо Round 1 ще не залочений (він генерується
одразу в момент Match Live Detected, §7 крок 1).

Наслідки:
- Кожен гравець, що встиг зайти, гарантовано бачить Round 1-питання від самого відкриття
  Arena.
- Однаково справедливо для Match 1/2/3 у Series — не потребує наперед відомого часу старту.

## 6. Answer window, reconnect, єдине відкрите питання

- **Reconnect** — generic-правило (soccer spec §9: відповідь, що дійшла до бекенду до lock, не
  карається; бекенд — source of truth) переноситься без змін.
- **Мінімальної тривалості answer window немає** (відмінність від soccer, де ≥60с
  гарантовані фіксованими 5-хв windows). Гравець змінює відповідь скільки завгодно, доки
  PredictionRound не залочений; лок без відповіді → `missed` → eliminated (звичайне правило).
- **Push-нотифікація при відкритті кожного PredictionRound** (мінімум — Round 1/13/24) —
  потрібна через непередбачувану тривалість вікон.
- **Інваріант: рівно одне відкрите питання одночасно** на Arena (каскадна модель, §7). Reconnect
  тривіальний: клієнт завжди запитує "поточне відкрите питання цієї Arena" і показує його —
  без потреби відстежувати історію.

## 7. Round Engine Flow (cascading generation)

1. **Match Live Detected** → генерується `PredictionRound` для Round 1. Round 1 **більше не
   фіксоване pistol-питання** — незважаючи на те, що це домен-факт pistol round (§2), питання
   вибирається так само, як для будь-якого раунду з кроку 7, з каталогу v1, стартуючи з
   **найнижчого** коефіцієнта складності (§10) — pistol-питання (~50/50) на самому вході в
   Arena призводило б до надмірної елімінації одразу на першому раунді. Answer window — до
   кінця freezetime Round 1.
2. **Round Lock** (кінець freezetime поточного раунду) →
   - поточний `PredictionRound` лочиться;
   - одразу генерується `PredictionRound` для наступного раунду, відкритий до кінця freezetime
     *цього* наступного раунду.
3. Крок 2 повторюється до кінця Match (`hasLiveGame() === false`).

   **Voided round.** Питання для раунду N+1 генерується в момент локу раунду N — до того, як
   відомий результат N. Якщо Match завершується, поки PredictionRound N+1 ще відкритий (або
   залочений, але не розпочатий) → переводиться у **`voided`** (нове значення
   `PredictionRound.status`, окрім `pending|open|locked|settled`). Voided — нейтральний: не
   впливає на elimination, не бере участі в settlement/leaderboard.

   **Порядок обробки на завершенні Match**: (1) спершу settle round N з останнього доступного
   снепшоту (той самий полл, що показав завершення), (2) лише після цього void round N+1 і
   пізніші згенеровані нерозпочаті раунди. Це запобігає помилковому voided round N, коли саме
   він виявився вирішальним для матчу.

   **Ризик даних**: GraphQL-фільтр `games(filter: { started: true, finished: false })` виключає
   гру з відповіді одразу по `finished: true`. Якщо це стається в тому ж ~10с інтервалі, що й
   вирішальний кіл, снепшот для settle round N може не існувати. Потребує підтвердження на
   живому API (§9, п.1); fallback — звірка з `seriesState.teams[].score`/`won`.
4. **Round 13** — єдиний раунд з фіксованим pistol-питанням: "Чи виграє команда `<X>`
   пістолетний раунд?" (`X` — випадкова команда). На відміну від Round 1, тут 50/50-складність
   прийнятна: до 13-го раунду гравці Arena вже "розігрілись" на попередніх (легших) раундах,
   і ризик масової елімінації нижчий, ніж на самому вході.
5. **Round 24** (якщо матч доходить) — фіксоване питання: "Чи буде рахунок 12-12 після цього
   раунду?". Settlement — пряме зчитування `games[0].teams[].score`: YES якщо обидва == 12, NO
   якщо один вже == 13. Якщо матч завершується раніше — Round 24 не генерується.
6. **OT-раунди (25+)** не мають окремого fixed-питання — обробляються як звичайні раунди (крок
   7), незалежно від внутрішньої OT-структури (MR3 чи інша). Кінець Match детектується завжди
   однаково (`hasLiveGame() === false`).
7. **Усі інші раунди** (2–12, 14–23, всі OT-раунди після 24) — тема з каталогу v1, вибрана
   рівномірно-випадково (Round 1 — окремий випадок, крок 1: найнижчий коефіцієнт складності
   з того самого каталогу; заплановане калібрування для решти раундів — §10):

   | Тема | Питання | Джерело даних | Settlement |
   |---|---|---|---|
   | **Переможець раунду** | "Чи виграє команда `<X>` цей раунд?" | `teams[].score` diff | Чия команда score зросла між снепшотом на лок і після завершення раунду |
   | **Зброя кілу** | "Чи буде хоч один кіл з `<зброя>` цим раундом?" (whitelist нижче) | `teams[].weaponKills[]` diff (сума обох команд) | YES якщо `count` обраної зброї зріс |
   | **TeamAce** | "Чи зробить кожен гравець команди `<X>` по кілу цим раундом?" | `teams[].players[].kills` diff, по 5 гравцях | YES якщо всі 5 per-player дельт == `1` |
   | **Multikill** | "Чи зробить команда `<X>` `<y>`-multikill цим раундом?" (`y` = 2..5) | `max()` per-player kills diff | YES якщо `max diff >= y` |
   | **Survivors (команда)** | "Чи залишиться в команді `<X>` більше ніж `<y>` виживших?" (`y` = 0..4) | `teams[].deaths` diff | YES якщо `5 - deaths_diff(X) > y` |
   | **Survivors (раунд)** | "Чи залишиться більше ніж `<y>` живих сумарно?" (`y` = 0..5) | `teams[].deaths` diff, сума обох команд | YES якщо `10 - total_deaths_diff > y` |

   **Whitelist зброї**: `awp, ak47, usp_silencer, deagle, molotov, glock, tec9, hegrenade`.

   **Settlement для всіх тем каталогу** — diff двох снепшотів (стан на лок раунду vs стан
   одразу після детекції завершення раунду), без потреби в per-event kill feed.

   **Свідомо виключено з v1**: перший кіл раунду (`firstKill` — прапорець на всю карту, не
   per-round сигнал), тімкіл цього раунду (надто рідкісний, скошено в бік NO), 3K+/ace через
   `multikills[]` (поле незаповнене в фіді), match point / вирівнювання рахунку (відкладено,
   не через брак даних).

## 8. Дані GRID: доступне і недоступне

**Доступно (надійно):**
- Рахунок серії (maps won) і карти (rounds won) — `teams[].score`.
- Номер раунду (виводиться), переможець раунду (diff рахунку).
- Годинник раунду (`clock.currentSeconds`, `ticksBackwards: true`, `ticking`) — детекція
  freezetime → live.
- `paused` — технічні паузи / warmup.
- Кумулятивні per-player/per-team: kills, deaths, assists, weaponKills, teamkills, selfkills,
  firstKill (прапорець, не подія), остання відома позиція.

**Недоступно** (інший GRID-фід): сторона CT/T, economy/buy-type, бомба (plant/defuse), kill
feed з точним часом/жертвою/зброєю/headshot, здоров'я/броня/live-статус гравця, явний прапорець
regulation vs overtime.

## 9. Відкриті питання

1. **Підтвердження Match Live Detected на живому API для Match 2/3 у Series** — гіпотеза
   побудована на історичних даних; перевірити на живому потоці перед реалізацією round engine.
2. **Спостережуваність фінального раунду Match** — чи гарантовано снепшот з фінальним рахунком
   з'являється до того, як `finished: true` виключає гру з відповіді (query-фільтр
   `started:true, finished:false`)? Потребує перевірки на живому API; fallback —
   `seriesState.teams[].score` (§7, Voided round).
3. **[Поза межами цієї специфікації]** Soccer-специфічний spec §9 (join-правило) розходиться з
   поточною реалізацією `arena-runtime.ts` (`hasLockedRound()`) — не стосується CS2, але варто
   синхронізувати окремо.

## 10. Калібрований добір складності питань (проміжний етап)

**Мотивація**: питання з каталогу (§7 п.7) наразі вибирається рівномірно-випадково — але деякі
(тема, параметр)-комбінації (напр. `Multikill y=5`, `Survivors y=4`, і сам pistol round —
статистично близький до 50/50) важко вгадати, інші сильно скошені в один бік і вгадати легко.
Без калібрування є ризик, що на ранньому раунді Arena гравцям випаде важке 50/50-питання і
значна їх частка вибуде, не встигнувши "розігрітись" у грі — саме тому Round 1 більше не
фіксоване pistol-питання (§7, крок 1), а обирається з найлегшого краю каталогу.

**Проміжний етап (перед впровадженням у round engine)**:

1. Записати (`GridRecorder`) **більше однієї гри/серії** — поточна вибірка
   (`cs2_series_28_...`) замала для статистично значущих базових ставок (base rates) по
   кожній (тема, параметр)-комбінації.
2. Для кожної комбінації з каталогу §7 п.7 (включно з pistol round — щоб мати порівнювану
   базову ставку для Round 13) обчислити емпіричну `P(YES)` по накопиченій вибірці — окремо
   для Переможця раунду, кожної зброї з whitelist, кожного `y` в
   TeamAce/Multikill/Survivors (команда)/Survivors (раунд).
3. **Коефіцієнт складності** — функція від відстані `P(YES)` до `0.5`: чим ближче до `0.5`,
   тим вищий коефіцієнт (важче вгадати); чим ближче до `0` чи `1`, тим нижчий (легше вгадати).
   Точна формула — деталь імплементації, не фіксується зараз.
4. **Порядок питань у Arena**: раунди на початку Arena (включно з Round 1, §7 крок 1)
   пріоритетно отримують теми/параметри з **низьким** коефіцієнтом складності, поступово
   дозволяючи вищий коефіцієнт у пізніших раундах. Точна крива (лінійна, ступінчаста тощо) —
   продуктове рішення, не фіксується зараз.

**Round 13 — свідомий виняток із кривої складності.** Фіксоване pistol-питання (~50/50)
залишається на Round 13 незалежно від того, яке місце в кривій складності воно б інакше
займало: до цього моменту гравці Arena вже пройшли кілька легших раундів, і ризик масової
