# CS2 Discipline — Specification v1 (HISTORY — superseded by spec_v2.md)

> **Архівний документ.** Лишений як історія grilling-сесії (хід думок, ітерації рішень,
> emпіричні дані з живих запитів). Актуальна специфікація — `spec_v2.md`.

> Вводить поняття **Discipline** та першу нефутбольну дисципліну — CS2. Дані беруться з GRID
> (`seriesState` GraphQL), а не з TxODDS. Фокус розробки зараз — тільки CS2; футбол активно не
> розвивається паралельно. Водночас у планах є додавання інших дисциплін у майбутньому, тож
> точки розширення (наскрізне поле `discipline` на `Match`, опціональне групування в Series)
> закладаються свідомо вже зараз — без передчасної уніфікації внутрішньої логіки round engine
> між дисциплінами, яка залишається дисципліно-специфічною (§3a).

## 1. Concept

CS2 — командна гра, де серія (`best-of-N`) складається з декількох карт (Games), кожна з яких
складається з раундів. На відміну від футболу (фіксовані 5-хвилинні windows, час іде вперед),
у CS2:

- раунд не має фіксованої тривалості за годинником матчу — він завершується подією (перемога
  команди), а не таймером;
- немає єдиного "матчевого годинника" — є `freezetime` (закупівля) → live-раунд (годинник тікає
  **назад**) → наступний раунд;
- дані надходять як **кумулятивний стан-снепшот** кожні ~10с (GRID `seriesState`), а не як
  потік дискретних подій.

Це вимагає окремого round engine для CS2 — не модифікації існуючого (soccer-специфічного), а
нового, паралельного.

## 2. Терміни (нові)

| Термін | Означення |
|---|---|
| **Discipline** | Тип гри (`soccer`, `cs2`, у майбутньому інші), що зберігається як поле `discipline` на `Match` і визначає, яка реалізація round engine, question-provider та ingestion обслуговує цей `Match`. |
| **Match (generic, contracts)** | Існуюча сутність `@arena/contracts` — дисципліно-агностична: **1 Match = 1 Arena завжди**, незалежно від дисципліни. Для soccer — це весь реальний матч. Для CS2 — це одна Game (карта); те, що розмовно називають "Game" в CS2-контексті, технічно є рядком `Match` з `discipline: "cs2"`. |
| **Series (CS2)** | Bo3 (чи інший `best-of-N`) — угруповання декількох `Match`-рядків (по одному на кожну карту), що відповідає GRID `seriesState`. **Не є окремою Arena** — Arena завжди на рівні одного `Match`/Game. Ідентифікується опціональним `seriesId` на `Match` (§3a); дисципліни без серійної структури (soccer) лишають це поле порожнім. |
| **Game** | Розмовний CS2-термін для одного `Match`-рядка (карти) в межах Series — див. вище. **Arena створюється на рівні Game, не Series** — кожна карта має власну арену, власний join, власний прогрес. |
| **Round (CS2)** | Один ігровий раунд CS2 всередині Game/Match. Номер раунду **не зберігається напряму** в GRID-даних — виводиться як `sum(games[0].teams[].score) + 1`. Не плутати з `PredictionRound` (сутність питання/ставки). |
| **PredictionRound** | Існуюча сутність (`@arena/contracts`) — вікно питання/ставки. Для CS2 прив'язується 1:1 до реального Round. |
| **Pistol Round** | Round 1 і Round 13 кожної Game (припущення формату MR12: пів по 12 раундів, 13-й — перший раунд другої половини). GRID-дані не мають прямого economy-сигналу — pistol round визначається виключно арифметично (номер раунду), без підтвердження стороннім полем. |
| **Game Live Detected** | Подія: GRID вперше показує обʼєкт Game з очікуваним `sequenceNumber` у `seriesState.games` (фільтр `started:true, finished:false`). Спостережувано на реальних даних: обʼєкт зʼявляється вже під час warmup (`paused:true`, `clock.ticking:false`), **до** початку Round 1 — тобто до реального старту гри лишається природний буфер (у зафіксованих даних ~140с / 14 полів по ~10с). |
| **Round Lock (CS2)** | Момент, коли PredictionRound для поточного раунду закривається для відповідей. Визначається як **кінець freezetime відповідного реального раунду** (момент, коли live-годинник починає тікати вниз), а не абсолютний час. |

## 3. Series / Match / Arena mapping

- Одна Arena = один Match-рядок = одна Game (карта), не вся Series.
- Series — не окрема таблиця/сутність, а угруповання `Match`-рядків через `seriesId` (§3a);
  арени створюються по одній на кожен `Match` (кожну карту) серії.
- **Проблема**: GRID API не дає наперед відомого часу старту для Game 2 і Game 3 — вони йдуть
  "follow-up" з невизначеною затримкою після завершення попередньої Game. Для **join-deadline**
  це вирішено (§4 — Game Live Detected, однаково для Game 1/2/3, без потреби в розкладі). Але
  для **моменту створення Arena** й **no-show timeout** запланований час старту таки знадобився
  знову — див. §3b, окремо від join-правила.
- Завершення Game (і, відповідно, arena) детектується так само, як в існуючому
  `GridRecorder`: `games` стає порожнім масивом (`hasLiveGame() === false`) після того, як Game
  була live — тобто карта завершена.
- Overtime не сигналізується жодним полем — виводиться правилом (рахунок ≥ 12:12 ⇒ подальші
  раунди понад регуляцію). Округлення/точний OT-формат (MR3 тощо) — **відкрите питання**,
  потребує підтвердження з GRID або продуктових правил.
- **Незалежність Games в межах Series**: кожна Game (карта) — повністю окрема Arena з власним
  `EntryPass` (окремий entry fee на кожну карту, не bundled на всю Series), власним survival-
  станом гравців і власним призовим пулом, який розподіляється одразу по завершенню цієї
  конкретної Game. Елімінація на Game 1 **не впливає** на можливість зайти в Arena Game 2 —
  немає наскрізного survival-стану на всю Series. Це узгоджується з базовим рішенням "Arena =
  один Match/Game", а не вся Series (§1) — не додає окремої "мульти-арени" концепції.

## 3a. Точка розширення для майбутніх дисциплін

Рішення прийняте зараз (не відкладене на "коли дійдемо"), бо в планах — додавання дисциплін
понад CS2 і soccer:

- **`Match.discipline: Discipline`** — нове поле на існуючій сутності `Match`
  (`@arena/contracts`), наразі відсутнє. `Discipline` — enum, `"soccer" | "cs2"`, розширюваний.
  За цим полем round engine / question-provider / ingestion-адаптер обираються фабрикою —
  той самий DI-seam, що вже існує (`RoundEngine` конструюється з інжектованим
  `QuestionProvider`), просто вибір конкретної реалізації тепер керується `discipline`, а не
  жорстко заданий на рівні коду.
- **`Match.seriesId?`** (опціональне) — FK на окрему сутність **`Series`** (`id, format,
  scheduledStartTime` — див. §3b), що належать одній Series (CS2 Bo3). Дисципліни без серійної
  структури (soccer) лишають поле порожнім. `Series` — легка сутність: тільки ці поля, без
  власного round-engine чи Arena-логіки (вони лишаються на рівні `Match`/Game, §3) — але, на
  відміну від початкового задуму "просто групування", вона таки **зберігає** дані (`format`,
  `scheduledStartTime`), що використовуються в бізнес-логіці (§3b), а не тільки для UI/агрегації.
- **Свідомо НЕ уніфікується**: внутрішня логіка round engine (fixed windows на годиннику
  матчу для soccer, vs event-driven каскад для CS2), формат питань і сетлмент — все лишається
  повністю дисципліно-специфічним за окремими реалізаціями інтерфейсу `QuestionProvider`.
  Примусова спільна абстракція над принципово різними доменами (таймер vs подія) дала б
  передчасну, шкідливу абстракцію — це свідомий trade-off, а не недогляд.
- **Join/lobby-правило (§4)** — виявилось таки CS2-специфічним (join до Game Live Detected, а
  не до локу Round 1), а не generic-абстракцією, як вважалось на попередній ітерації grilling.
  Реалізується як CS2-специфічна перевірка в Arena join-хендлері (аналог `hasLockedRound()`,
  але з умовою по Game Live Detected замість round-статусу), не потребує зміни generic Arena
  API — лише discipline-specific підміна умови.
- **Tie-break наприкінці Game теж перевикористовує generic-правило.** Якщо Game завершується
  (команда набрала потрібну к-сть перемог), а кілька гравців ще живі без жодної помилки —
  застосовується вже існуюче правило spec_v2 §12 "shared win → рівний поділ призового пулу між
  tied winners". Нового CS2-специфічного tie-break критерію **не потрібно** — Game просто
  закінчується (аналогічно full_time у футболі), і всі, хто дожив, трактуються як tied winners.
- Фіксовані спеціальні раунди (pistol round 1/13, OT-раунд 24, §5 п.4/4a) — це
  **CS2-специфічний** хук у CS2-реалізації `QuestionProvider`, не generic-концепція на рівні
  contracts. Інші дисципліни, якщо матимуть аналогічну потребу (напр. "перший сет" у волейболі),
  реалізують це у власному `QuestionProvider`, без спільного механізму "fixed round" в
  contracts.

## 3b. Arena lifecycle через Series: створення, дострокове завершення, no-show

**Поля сутності `Series`** (окрема легка сутність, `Match.seriesId` — FK на неї, §3a):

- `format: number` — **ціле число** N = максимальна к-сть ігор у форматі (`1..7`: Bo1=1, Bo2=2,
  Bo3=3, Bo4=4, Bo5=5, Bo6=6, Bo7=7), не рядковий enum. Разом з `winsNeeded` (нижче) з нього
  завжди можна вивести все потрібне; окремо зберігати `winsNeeded` не потрібно.
- `scheduledStartTime` — **гарантовано присутнє й надійне** значення (вручну введене оператором
  або окремо спарсене з GRID під час створення Series у базі — деталь імплементації, але сам
  факт наявності значення не під сумнівом). Це знімає попередній "open question" про джерело
  розкладу (§7, було п.7) — воно більше не блокер.

**Створення Arena по ходу Series:**

1. **Arena #1** (Game 1) створюється автоматично в стані `lobby` за **10 хв до**
   `scheduledStartTime` (значення затверджене, див. нижче). Join у неї відкритий
   одразу після створення, закривається на Game Live Detected (§4) — це не суперечить одне
   одному: Arena може існувати й приймати entry pass задовго до Game Live Detected.
2. **Arena #k+1** створюється **реактивно**, одразу по завершенню Game k (`hasLiveGame()` стає
   `false` після того, як Game k була live) — **за умови, що Series ще не вирішена** (див.
   нижче). Номер наступної гри (`k+1`) — це просто наш власний послідовний лічильник створених
   Arena для цієї Series; **не потрібно** вираховувати чи звіряти його з будь-яким полем GRID
   (напр. `sequenceNumber`) — ми самі керуємо порядком.
3. **Перевірка "Series вирішена"** — перед створенням Arena #k+1 перевіряються **дві незалежні
   умови**, Arena #k+1 не створюється, якщо виконується **будь-яка** з них:
   - `k >= format` — усі ігри формату вже зіграно (немає "гри понад ліміт");
   - будь-яка команда вже досягла `winsNeeded = floor(format / 2) + 1` перемог у
     `seriesState.teams[].score` (early clinch, до вичерпання формату).

   Обидві умови потрібні одночасно через **Bo2 (`format = 2`)**, де можлива **нічия в серії**
   (1-1): для Bo2 `winsNeeded = 2`, що дорівнює самому `format` — тобто early clinch тут
   спрацьовує лише на повному sweep (2-0), а рахунок 1-1 ловиться саме умовою `k >= format`, не
   `winsNeeded`. Для непарних форматів (Bo3/Bo5/Bo7) нічия неможлива за означенням, і обидві
   умови завжди збігаються в одній і тій самій точці.

   Це єдине правило покриває без розрізнення:
   - **Нормальне дострокове завершення** (напр. Bo3 закінчується 2-0, Game 3 не потрібна);
   - **Нічию у форматі, що її допускає** (Bo2, рахунок 1-1 після 2 ігор);
   - **Форфейт всередині Series** (команда знялась після Game k, рахунок серії це так само
     відображає).
4. **No-show на Game 1 (вирішено)**: якщо Game Live Detected не настає протягом **60 хв** після
   `scheduledStartTime`, Arena #1 переводиться зі стану `lobby` напряму в `cancelled`/закрита,
   без переходу в `live`, а **вся Series позначається недійсною** (не лише ця Arena — подальше
   створення Arena #2/#3 для цієї Series також блокується, хоча на практиці вони й так ще не
   існували б на цьому етапі). Уже куплені `EntryPass` переводяться в `status: refunded` —
   використовує вже існуюче поле `EntryPass.status` (`@arena/contracts`), нової сутності не
   потрібно.
5. Форфейт **всередині вже live Game** (команда здалась посеред раунду) — окремого правила не
   потрібно: це вже покривається загальною логікою "Game завершилась" (§5, `hasLiveGame() ===
   false`), Arena переходить у `finished` як завжди, tie-break див. §3a.

**Push-нотифікація "нова Arena відкрита".** Окремо від §4a (нотифікація про нове відкрите
питання всередині Game) — коли створюється Arena #k+1 (крок 2), усім учасникам попередньої
Arena Series (незалежно від того, вижили вони чи вибули) надсилається push: нова карта
доступна, можна спробувати сили. Це окремий, ширший тригер, ніж per-round нотифікація.

**Значення затверджені**: Arena #1 створюється за **10 хв** до `scheduledStartTime`; no-show
timeout — **60 хв** після `scheduledStartTime` без Game Live Detected.

## 4. Join / Lobby правила

**Рішення (переглянуто): T-2хв правило скасовується, але CS2 таки отримує власне
discipline-specific join-правило** — не зводиться до generic Arena-правила spec_v2 §9. Це
уточнення пройшло через кілька ітерацій під час grilling:

1. Спершу: T-2хв до старту (виявилось нежиттєздатним — немає наперед відомого часу старту для
   Game 2/3).
2. Потім: повне скасування на користь generic-правила "join до локу Round 1" (реалізовано в
   коді як `hasLockedRound()` grace window, `apps/api/src/gateway/arena-runtime.ts:180-204` —
   **не** в письмовому тексті spec_v2.md §9, який досі каже "тільки до старту арени"; це
   розходження коду й документа, виявлене під час grilling, саме по собі варте окремого
   виправлення поза межами цієї специфікації).
3. **Фінальне рішення**: у CS2 join в Arena дозволений **тільки до моменту Game Live Detected**
   (§2) — суворіше, ніж generic-правило "до локу Round 1". Після Game Live Detected Arena
   закрита для нових гравців (лише spectate), **навіть якщо** Round 1 ще не згенерований і не
   залочений (він генерується одразу в момент Game Live Detected, §5 крок 1).

Наслідки цього рішення:

- Кожен гравець, що встиг зайти в Arena, гарантовано бачить Round 1/13-question від самого
  його відкриття (немає сценарію "зайшов під час warmup і застав питання вже відкритим
  частково") — простіше й детермінованіше за generic-правило, ціною коротшого вікна для
  приєднання (немає join під час warmup, на відміну від попередньої ітерації рішення).
- Однаково справедливо для Game 1, 2 і 3 — не потрібне наперед відоме "заплановане час старту"
  (open question про GRID schedule endpoint лишається знятим).
- Це **CS2-специфічне** правило (аналогічно до fixed pistol/OT-питань), не generic-абстракція
  на рівні Arena — на відміну від того, що стверджувалось на попередній ітерації grilling
  (виправлено вище, §3a).

## 4a. Answer window, reconnect і "єдине відкрите питання"

**Reconnect-механізм не потребує CS2-специфічних змін.** Generic-правило spec_v2 §9
("відповідь дійшла до бекенду до lock → не карається", бекенд — source of truth) повністю
незалежне від тривалості вікна відповіді — переноситься на CS2 без модифікацій.

**Мінімальної тривалості answer window для CS2 немає (свідома відмінність від soccer).**
Soccer вимагає (spec_v2 §5) щонайменше 60с на роздуми — фіксовані 5-хвилинні windows це
гарантують. CS2 не може дати такої гарантії: найкоротший спостережений повний цикл раунду в
живих даних — 65с, але теоретичний мінімум (дуже швидкий вайп + фрізтайм наступного раунду)
може бути суттєво коротшим (~25-30с). **Рішення**: CS2 не встановлює мінімальний поріг і не
пропускає раунди через це. Гравець може змінювати відповідь скільки завгодно раз, доки
PredictionRound не залочений; якщо лок стався без відповіді — `missed` → eliminated (звичайне
правило §6 spec_v2, без змін).

**Наслідок — потрібні push-нотифікації.** Оскільки вікна відповіді можуть бути короткими й
непередбачуваними (на відміну від соккера, де гравець орієнтується на 5-хвилинні мітки), гравцю
потрібен спосіб дізнатись про нове відкрите питання, не тримаючи вкладку постійно у фокусі.
**Новий продуктовий пункт**: push notification при відкритті кожного PredictionRound (або
щонайменше — при відкритті Round 1/13/24), щоб гравець встиг повернутись і відповісти до locку.
Деталі реалізації (web push, in-app, etc.) — поза межами цієї специфікації.

**Інваріант: рівно одне відкрите питання одночасно.** Каскадна модель (§5) гарантує, що для
однієї Arena в кожен момент часу існує **не більше одного** `PredictionRound` у статусі `open`.
Це робить reconnect/resync тривіальним: клієнт, що перепідключився (закрив і відкрив сторінку
заново), завжди запитує в бекенду "поточне відкрите питання цієї Arena" і показує саме його —
без потреби відстежувати історію чи розбиратись, який раунд "актуальний". Це той самий
"ресинк з поточним станом арени/раунду" з spec_v2 §9, застосований до CS2 без змін.

## 5. Round Engine Flow (cascading generation)

На відміну від soccer round engine (заздалегідь відомі фіксовані вікна), CS2 round engine
працює каскадно, керуючись подіями, а не годинником:

1. **Game Live Detected** → одразу генерується `PredictionRound` для Round 1.
   - Питання Round 1 **завжди** фіксоване: "Чи виграє команда `<X>` пістолетний раунд?"
     (`X` — одна з двох команд, обирається випадково).
   - Answer window відкрите, доки не завершиться freezetime Round 1 (реальний раунд стає live).
2. **Round Lock** (кінець freezetime поточного раунду) →
   - Поточний `PredictionRound` лочиться.
   - **Одразу** генерується наступний `PredictionRound` (для наступного номера раунду).
   - Новий `PredictionRound` лишається відкритим, доки не завершиться freezetime *цього*
     наступного раунду — тобто його answer window охоплює: залишок live-фази попереднього
     раунду + перехід/scoreboard + freezetime нового раунду.
3. Крок 2 повторюється до кінця Game (`games` стає порожнім / Game завершена).

   **Voided round (загальне правило).** Питання для раунду N+1 генерується в момент локу
   раунду N — тобто **до** того, як відомий результат раунду N. Це означає, що на кожному
   переході N→N+1 теоретично можливий сценарій "раунду N+1 не буде" (раунд N виявився
   вирішальним — команда набрала 13 перемог і Game завершилась). Найочевидніше це проявляється
   на переході 24→25 (доля продовження в OT невідома до самого кінця раунду 24), але правило
   загальне для будь-якого N.

   Якщо Game завершується (детектується як `hasLiveGame() === false`) поки PredictionRound для
   ще не розпочатого раунду N+1 вже відкритий (або навіть вже залочений, якщо не встигли
   зловити стан вчасно) — цей PredictionRound переводиться у стан **`voided`**. Voided-раунд
   **нейтральний**: не впливає на elimination жодного гравця незалежно від того, встиг він
   відповісти чи ні, і не бере участі в settlement/leaderboard розрахунках. Це вимагає
   розширення `PredictionRound.status` (`@arena/contracts`) новим значенням `voided` — статус
   `pending|open|locked|settled` наразі такого стану не передбачає.

   **Важливе застереження — не voided-ити раунд, що вирішив матч.** Round Lock раунду N
   відбувається на *початку* його live-фази — тобто задовго до того, як результат раунду N
   стає відомим. Сетлмент round N відбувається пізніше: коли поллінг показує приріст рахунку
   після завершення раунду. Якщо саме round N виявляється вирішальним для матчу (команда
   набрала 13 перемог), то "Game завершилась" і "у round N щойно з'явився остаточний,
   settle-able результат" — це **одна й та сама подія з одного й того самого полу**. Обробник
   Game-finished **не повинен** сліпо `void`-ити всі не-`settled` PredictionRound на момент
   детекції завершення — інакше round N (який мав нормальний, відомий результат) помилково
   потрапить у `voided` разом із round N+1 (який справді ніколи не відбувся). Правильний
   порядок обробки: (1) спершу спробувати settle round N з останнього доступного снепшоту
   (той самий полл, що показав завершення), (2) лише після цього void-ити round N+1 (і будь-які
   пізніші вже згенеровані, але нерозпочаті раунди).

   **Відкритий ризик даних**: GraphQL-запит фільтрує `games(filter: { started: true, finished:
   false })` — щойно GRID позначає гру `finished: true`, вона повністю зникає з відповіді,
   разом із фінальним рахунком раунду N. Якщо GRID виставляє `finished` в межах того самого
   ~10с інтервалу поллінгу, коли стався вирішальний кіл (тобто жоден полл не встигає застати
   гру ще "живою", але вже з фінальним рахунком) — снепшоту для settle round N може просто не
   існувати. У записаній вибірці цей момент не зафіксований (запис зупинився в середині гри),
   тож емпірично не перевірено. Потребує підтвердження на живому API перед імплементацією;
   можливий fallback — звірка з `seriesState.teams[].score`/`won` (рахунок серії, мап-вон),
   який має оновитися незалежно від того, чи game-об'єкт ще потрапляє під фільтр.
4. **Round 13** — так само, як Round 1: питання завжди фіксоване ("чи виграє команда `<X>`
   пістолетний раунд?", команда випадкова, незалежно від того, яка команда була обрана на
   Round 1).
4a. **Round 24** (якщо матч доходить до нього) — питання завжди фіксоване: "Чи буде рахунок
    12-12 після цього раунду? (овертайм)". Settlement — пряме зчитування
    `games[0].teams[].score` після раунду: YES, якщо обидва score == 12; NO, якщо один з них
    вже == 13 (матч вирішено в регуляції). Технічно найнадійніша тема з усіх — пряма рівність
    полів, без diff'ів. Якщо матч завершується раніше 24-го раунду (одна з команд вже здобула
    13 перемог), Round 24 просто ніколи не генерується — крок 3 (кінець Game) спрацьовує
    раніше.

    **OT-раунди (25+) не мають окремого fixed-питання.** На відміну від Round 1/13/24, для
    жодного раунду овертайму немає спеціальної теми — усі OT-раунди обробляються як **звичайні**
    раунди з кроку 5 (рандомна тема з каталогу), незалежно від того, чи це перший раунд OT-
    періоду з "economy reset" (структурно схожий на pistol round), чи ні. Точний формат OT
    (MR3 чи інший — §7.2) **не потрібен** для роботи round engine: кінець Game детектується
    завжди однаково (`hasLiveGame() === false`), незалежно від внутрішньої OT-структури рахунку.
    Емпірично підтверджено на реальних даних серії 28: перехід regulation→OT (рахунок 12-12 →
    12-13, розрив ~4хв з нестабільним годинником і довгою паузою) **не** призводить до
    зникнення `games` з відповіді чи `finished: true` — Game лишається "живою" протягом усього
    переходу, тож ризик хибного "Game finished" на цій межі **знятий**.
5. **Усі інші раунди** (2–12, 14–23, і всі раунди OT після раунду 24) — питання генеруються
   рандомно з **фіксованого каталогу v1 (6 тем)**:

   | Тема | Питання | Джерело даних | Settlement |
   |---|---|---|---|
   | **Переможець раунду** | "Чи виграє команда `<X>` цей раунд?" (`X` — випадкова команда) | `games[0].teams[].score` diff | Порівняти, чия команда score зріс між снепшотом на лок раунду і снепшотом після завершення раунду |
   | **Зброя кілу** | "Чи буде хоч один кіл цим раундом здійснено з `<зброя>`?" (`зброя` — випадкова з whitelist) | `games[0].teams[].weaponKills[]` diff (сума по обох командах) | YES, якщо `count` для обраної зброї зріс між снепшотом на лок раунду і снепшотом після завершення раунду |
   | **TeamAce** | "Чи зробить кожен гравець команди `<X>` по одному кілу цим раундом?" (`X` — випадкова команда) | `games[0].teams[].players[].kills` diff, по кожному з 5 гравців команди | YES, якщо всі 5 per-player дельт `kills` між снепшотом на лок раунду і снепшотом після завершення раунду дорівнюють рівно `1` (сума = 5, розподілена порівну) |
   | **Multikill** | "Чи зробить команда `<X>` `<y>`-multikill цим раундом?" (`X` — випадкова команда, `y` — випадкове число 2..5) | `games[0].teams[].players[].kills` diff, `max()` по 5 гравцях команди | YES, якщо `max(per-player kills diff)` >= `y` (щонайменше y kills одним гравцем; не залежить від `multikills[]`) |
   | **Survivors (команда)** | "Чи залишиться в команді `<X>` більше ніж `<y>` виживших гравців?" (`X` — випадкова команда, `y` — випадкове число 0..4) | `games[0].teams[].deaths` diff (командний рівень, без потреби в per-player) | YES, якщо `5 - deaths_diff_цього_раунду(X)` > `y` |
   | **Survivors (раунд)** | "Чи залишиться в цьому раунді більше ніж `<y>` живих гравців сумарно (обидві команди)?" (`y` — випадкове число 0..5) | `games[0].teams[].deaths` diff, сума по обох командах | YES, якщо `10 - (усі смерті цього раунду по обох командах)` > `y` |

   **Whitelist зброї (вирішено)**: `awp, ak47, usp_silencer, deagle, molotov, glock, tec9,
   hegrenade`. Обрано за живими даними серії 28 (кумулятивні кіли за карту): `ak47`×41,
   `awp`×15, `usp_silencer`×6, `tec9`×4, `deagle`×3, `glock`×3, `molotov`×2, `hegrenade`×1.
   Свідомо не включені `m4a1_silencer`(25), `mp9`(12), `galilar`(6), `m4a1`(5), `mac10`(4),
   `fiveseven`(4), `elite`(3), `p250`(1), `famas`(1) — за продуктовим рішенням, не за
   відсутністю даних (поле `weaponKills[].weaponName`/`count` покриває їх так само надійно).

   *Survivors перевірено на живих даних*: розподіл виживших по команді за раунд (58
   team-раундів) — `0×26, 1×9, 2×8, 3×7, 4×8`; сумарних виживших за раунд (29 раундів) —
   `0×2, 1×2, 2×9, 3×6, 4×10`. У цій вибірці жоден раунд не дав сумарно 5+ виживших — тобто
   тема "Survivors (раунд)" з `y=4` чи `y=5` матиме дуже низьку базову ймовірність YES
   (аналогічно до свідомо прийнятого трейд-офу в Multikill/TeamAce), але формула коректна й
   не залежить від вибірки. Двічі за 29 раундів обидві команди одночасно закінчили раунд з
   0 виживших (взаємне знищення) — валідний, хоч і рідкісний, результат.

   *TeamAce і Multikill перевірено на живих даних*: per-round diff по `players[].kills` для
   всіх 30 раундів вибірки поводиться коректно і без пропусків (сума приросту команди-
   переможця стабільно 4–5 за раунд). Розподіл `max(per-player kills diff)` на 58
   team-раундах вибірки: `1K`×20, `2K`×26, `3K`×9, `4K`×3, `5K/ace`×0 (не траплялось у цій
   грі, але формула ідентична TeamAce). Обидві теми **не залежать** від непідтвердженого
   поля `multikills[]`.

   **Свідомо виключено з v1** (розглянуто і відхилено під час grilling):
   - *Хто зробить перший кіл раунду* — неможливо: `firstKill` не є per-round прапорцем.
     Перевірено на живих даних (`sabg_raw.cs2_series_28_...`, 30 раундів): прапорець
     переключився `false→true` рівно **один раз за всю карту** (раунд 1), далі жодних змін —
     тобто це "чи гравець хоч раз за карту відкрив рахунок", а не сигнал конкретного раунду.
   - *Тімкіл цього раунду* — технічно виводиться (`teamkills` diff), але за 30 спостережених
     раундів жодної події не було: сильно скошена в бік NO тема, низька ігрова цінність.
   - *Мультікіл (3K/4K/ace)* — поле `multikills[]` порожнє у всіх 331 знімках вибірки; не
     підтверджено, що GRID взагалі його заповнює для цього фіда.
   - *Match point / вирівнювання рахунку / серія перемог поспіль* — розглядались як Tier 1
     (чиста арифметика рахунку, без ризиків), але не обрані для v1 за продуктовим рішенням;
     можуть бути додані пізніше без потреби в нових даних.

**Наслідок для settlement**: обидві теми v1 сетляться діафом двох снепшотів (стан на момент
локу раунду vs стан одразу після детекції завершення раунду) — без потреби в per-event kill
feed.

## 6. Дані GRID: що доступно, а що ні

Джерело: `sabg_raw.cs2_series_28_20260729T124049694Z` (331 знімків, ~10-11с інтервал,
кумулятивний стан, без дискримінатора типу події).

**Доступно (надійно):**
- Рахунок серії (maps won) і рахунок карти (rounds won) — `teams[].score`.
- Номер раунду — виводиться (`sum(score)+1`).
- Переможець раунду — diff рахунку між сусідніми знімками.
- Годинник раунду (`clock.currentSeconds`, `ticksBackwards: true`) і `ticking` — для детекції
  переходу freezetime → live.
- `paused` — детекція технічних пауз / warmup.
- Кумулятивні per-player/per-team: kills, deaths, assists, weaponKills, teamkills, selfkills,
  firstKill (прапорець, не подія), позиція гравця (останній відомий x/y).

**Недоступно (потребує іншого GRID-фіда, не того, що зараз пишеться):**
- Сторона CT/T.
- Economy / buy-type (eco/force/full buy), гроші команди.
- Бомба (plant/defuse, таймер).
- Kill feed з точним часом/жертвою/зброєю/headshot.
- Здоров'я/броня/статус "живий" гравця.
- Явний прапорець regulation vs overtime.

## 7. Відкриті питання

1. ~~Каталог тем для не-пістолетних питань~~ — **вирішено** (§5): 6 тем, включно з "зброя
   кілу" (whitelist `awp, ak47, usp_silencer, deagle, molotov, glock, tec9, hegrenade`
   зафіксовано).
2. ~~Overtime формат~~ — **знижена критичність** (§5, п.4a): round engine не потребує знання
   точного OT-формату (MR3 чи інший), оскільки OT-раунди обробляються як звичайні (без
   спеціальних fixed-питань), а кінець Game детектується уніфіковано через `hasLiveGame()`.
   Гіпотеза MR3 підтверджена непрямо на живих даних серії 28 (прогресія рахунку в OT не
   суперечить формату "6 раундів на період, перша до 4"), але формальне підтвердження більше
   не є блокером для імплементації.
3. **Підтвердження "Game Live Detected" на живому API для Game 2/3** — гіпотеза побудована на
   історичних даних Game 1/2 в межах однієї записаної серії; варто перевірити на живому потоці
   безпосередньо перед реалізацією round engine.
4. ~~Дискримінація дисципліни в `@arena/contracts`~~ — **вирішено на рівні дизайну** (§3a):
   `Match.discipline` + опціональний `Match.seriesId`, вибір round engine/question-provider за
   `discipline` через існуючий DI-seam. Залишається імплементаційна деталь: конкретний механізм
   фабрики (registry/switch) — не потребує окремого дизайн-рішення, вирішується під час
   імплементації за існуючими патернами коду.
5. **Спостережуваність фінального раунду Game** — чи гарантовано GRID показує снепшот з уже
   оновленим фінальним рахунком *до* того, як `finished: true` виключає гру з відповіді
   (query-фільтр `started:true, finished:false`)? У записаній вибірці момент завершення гри не
   зафіксований (запис зупинився в середині гри) — потрібна перевірка на живому API. Якщо
   підтвердиться, що снепшот втрачається, знадобиться fallback через `seriesState.teams[].score`
   (§5, "Voided round").
6. **[Поза межами цієї специфікації] `spec_v2.md` §9 розійшовся з кодом.** Письмовий текст
   каже "join дозволений тільки до старту арени", але `arena-runtime.ts` (`hasLockedRound()`)
   реалізує грейс-вікно "до локу першого раунду", з коментарем, що (помилково) посилається на
   spec §9. Виявлено під час grilling CS2 join-правила (§4); варто окремо синхронізувати
   spec_v2.md з фактичною поведінкою коду для футбольної дисципліни — не стосується CS2, але
   лишати як є ризиковано для майбутніх дисциплін, що спиратимуться на generic Arena-поведінку.
7. ~~Джерело `scheduledStartTime` для Series~~ — **вирішено** (§3b): значення гарантовано
